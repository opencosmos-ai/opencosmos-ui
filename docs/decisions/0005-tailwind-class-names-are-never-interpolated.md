# 0005 — Tailwind class names are never built by interpolation

**Date:** 2026-06-01 · **Status:** Accepted · **Relates to** [0003](0003-precompiled-styles-css-over-a-consumer-safelist.md)

_`gap-${n}` appears literally nowhere, so Tailwind never emits the utility and the component renders unstyled with no error — the rule is enforced by a test, not by review._

## Context

`Grid`, `GridItem`, and `Stack` built their layout classes at runtime: `` `gap-${gap}` ``, `` `grid-cols-${cols}` ``, and responsive variants assembled as `` `md:${cls}` ``. This reads as obviously correct and is obviously correct in JavaScript terms — the right string reaches `className`.

Tailwind's compiler never sees it. It scans source text for complete static class literals; a name that only exists after string concatenation at runtime appears in the source nowhere at all. The utility is silently never generated.

The components shipped that way. In consuming apps `Grid` collapsed to a single full-width column with no gap. The class was in the DOM, the compiler had emitted no rule for it, and nothing anywhere reported a problem. This is the same silent-omission failure mode as the safelist in [0003](0003-precompiled-styles-css-over-a-consumer-safelist.md), arriving by a different route.

It is a rule that cannot survive on documentation alone. Interpolating a class name is the natural way to write the code, it looks right in review, and it only fails in someone else's application.

## Decision

Never interpolate a Tailwind utility. Layout classes resolve by indexing into exhaustive static-literal maps in [`packages/ui/src/lib/responsive-classes.ts`](../../packages/ui/src/lib/responsive-classes.ts), which are generated by `pnpm --filter @opencosmos/ui gen:responsive-classes`.

The rule is enforced by [`packages/ui/src/test/no-dynamic-classes.test.ts`](../../packages/ui/src/test/no-dynamic-classes.test.ts), which scans component source for a Tailwind prefix immediately followed by `${` and fails the build. **Fix the class; never disable the test.**

The prefix list in that test is deliberately limited to multi-character, unambiguous utilities, so it does not fire on unrelated interpolations like a React `key={`h-${i}`}`. It is not a complete guard against every possible dynamic class — it is a guard against the family of mistakes that has actually happened, and it is cheap to extend when a new one does.

## Consequences

- Layout components are verbose where they were concise: an exhaustive map of every allowed value instead of arithmetic. That verbosity is the point — every class exists as a literal the compiler can find.
- The maps are generated, so extending a scale means regenerating rather than hand-editing.
- The guardrail is a test rather than a lint rule, so it runs wherever the test suite runs. Note that CI's test step currently filters on a package name that no longer exists (`@thesage/ui`, renamed to `@opencosmos/ui` in March 2026), so it matches no projects and passes vacuously — the guardrail is real but is not presently being run in CI.
- Any new component with a numeric or responsive prop hits this constraint immediately, which is the intended moment to discover it.

## Alternatives considered

- **Safelist the interpolated classes.** Rejected: it is the same hand-maintained list that failed in [0003](0003-precompiled-styles-css-over-a-consumer-safelist.md), and it would have to live in this package's build rather than the consumer's.
- **Inline styles for gaps and columns.** Rejected: it takes those values out of the token system, so they stop responding to theme and stop matching the rest of the library.
- **Document the rule and rely on review.** Rejected: it was documented, and the bug shipped anyway. The failure is invisible in this repository — it only appears in a consumer — so nothing short of a mechanical check catches it in time.
